Thesis

Different machines.Same problem.

Across audio, mechanical systems, fabrication, controls, software, and AI, I keep coming back to the same task: trace what moves through the system, understand what transforms it, find what controls it, and follow the result all the way into reality.

This is how I tend to model technical problems: trace the signal through transformation, routing, control, interface, feedback, and consequence.

I tend to troubleshoot from both ends: follow the signal forward toward consequence, then use feedback to work backward from what reality actually did.

PAC demonstrator

PAC explores whether a machine has legitimate, current authority for a specific physical action, separately from whether it can perform that action and whether the action is independently safe.

OFFLINE — VERIFIED TRACE REPLAY Recorded outcomes of cases D01–D05, replayed in this browser. This is not live PAC adjudication, and no physical robot or actuator is connected: the schematic arm in the background is a drawing.

  • D01 — Authorized actionPAC returns PERMIT, independent safety returns ALLOW, and the simulated action reaches EXECUTED.
  • D02 — Missing authorityRequired institutional work permission is missing. PAC returns DENY and no execution occurs.
  • D03 — Consumed authorityA previously consumed authorization instance is replayed without re-adjudication. Execution is refused as AUTHORITY_CONSUMED.
  • D04 — Independent safety vetoPAC returns PERMIT, but independent safety returns DENY. No execution occurs.
  • D05 — Unknown mandatory evidenceMandatory asset identity is UNKNOWN. PAC returns DEFER, no authorization is issued, and no execution occurs.
